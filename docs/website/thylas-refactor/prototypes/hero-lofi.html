The workspace

Five areas, because there are five things a person does here: orient, organise, think, delegate, administer. Each is labelled with what it is today — not with what it is meant to become.

01

Workspace & Files

In the build

The central object. Everything you open — a file, a note, a board, a run — lives inside a workspace scope, and the scope survives tabs, sessions and switching. File tree, table and preview are navigable; upload is not connected yet.

02

Notes & Documents

In development

Markdown-first knowledge management: [[wikilinks]], backlinks, autosave, conflict handling. Obsidian-inspired, minus the plugin market.

03

Whiteboard

In development

Spatial boards for thinking in parallel: cards, sections, edges, zoom to pointer, undo. Heptabase-inspired. A card can be authored (yours, editable) or live (owned by a run, read-only).

04

Processes

In the build

The interface for delegated work: five states — queued · running · needs you · done · failed — filters, and a run detail view. Today it runs on a labelled simulator; the view is built to be fed by WAM.

AI

In development

One capability, done honestly: a question answered by DeepSeek through a server-side endpoint, labelled DeepSeek · dev endpoint. It answers; it never pretends to start a process.

03

Beyond a conventional workspace

Thylas is built against three products it refuses to be. Each refusal decides something concrete about the interface.

Not a productivity workspace

In Notion or Heptabase, every object was made by a person. Thylas has a second class: work delegated elsewhere, with a lifecycle nobody controls — it can change while you are not looking.

State is a first-class element. A running job is never visually indistinguishable from a finished note.

Not a chat product

Chat orders everything by time and dies with the session. The conversation is a good input method and a bad organising principle.

Intent is taken as text, then filed as an object. The record is the plan and the artifacts, not the transcript.

Not a cloud console

A console reports on the provider's resources. Thylas answers a different question: did your work move forward, and what needs you.

Overview orients; cost lives in Account, one click away.

And one thing none of them have: provenance. Every artifact carries which run produced it — and removing a file breaks the things that reference it.

04

Architecture

The distinction is not "UI versus backend". It is which state each component is the authority for.

Thylas owns — working state

  • Which workspace, what is open
  • Where a note lives, what a board looks like
  • What you named things, what you have seen
  • Files, notes, boards, preferences, open tabs

WAM owns — reasoning state

  • What the intent means
  • What the plan is, and its revisions
  • Which agent is running, what is shared across sessions
  • Run state, scheduling, retry, model choice

If a Thylas screen has to decide something about your work, the screen is wrong. Thylas collects the instruction, WAM decides, Thylas reports.

Position within CHORD: WAM is the orchestration layer and Thylas's future counterpart — not connected yet. Rym, the model layer, is called by WAM, never by Thylas. Knock is the community, out of scope by decision, linked at most.

05

Design philosophy

The product is built as an instrument, not a dashboard. Three principles carry most of that weight.

P·1

Continuity

Every boundary is a 1px line that runs the full length of its region. Raised surfaces are lighter; recessed are darker. Never the reverse.

P·2

Structure

A 4px grid, seven type steps, one accent reserved for state. Hue never encodes structure: remove all colour and the layout still reads.

P·3

Agency

The material is yours. Authored objects are editable; delegated objects are read-only until they land. The interface reports state instead of making decisions.

The one-sentence test: cover the logo. If the surface could be mistaken for project-management SaaS, something on it is generic.
